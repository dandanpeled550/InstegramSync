# M0 — Setup

**Goal:** the repo, tooling, contracts and accounts are ready, so M1 can start building the receiver.
**Done when:**
1. M0.5 (initial schema) merges into `dev` with every required check green (incl. `ci/migrations`), and the
   resulting `deploy-staging` run is green **with `db push` actually run** — the schema is live on `insta-saver-dev`.
2. Release `v0.1.0` is merged into `main` by the human, and the resulting `deploy-production` run is green
   and created the `v0.1.0` tag.

This refines `docs/PLAN.md` §9 ("first PR merged into `dev` deploys to staging"): PR #1 merged before CI
existed, so the criterion is tied to the first PR that has something to deploy.

## Open questions for the human

- **Q1 — `SECURITY.md` vs. skipped H3.** Either turn on private vulnerability reporting (one toggle in repo
  Settings → Security), or have devops-engineer change `SECURITY.md` to another contact route. Until then the
  public repo advertises a reporting channel that doesn't exist.
- **Q2 — agents can forge review statuses.** All agents share one `gh` identity, so any agent could post
  `agent-review/security=success` (or `agent-review/code`) via `gh api`, or remove the `security` label.
  Rulesets can't restrict a check to one sender here. Fix is a PreToolUse hook in `.claude/**` — **humans
  only** — that blocks writes to `agent-review/*` statuses and `security`-label removal for every agent
  except the matching reviewer. Your call: add the hook, or accept the risk for now.

### M0.2 — CI, tooling, labels, branch protection script
- Owner: devops-engineer · Branch: `chore/m0-ci-tooling` → PR into `dev` · Labels: `M0`, `area:devops`, `security`, `agent:devops-engineer`
- Contracts: none (follows `docs/AGENTS_PLAN.md` §15.4–15.5).
- In scope: `Makefile` (targets: `dev`, `test`, `lint`, `fmt`, `process`, `process-prod` stub with the
  main/clean/tag check, `replay` stub); `.github/workflows/pr-checks.yml` (`ci/lint`, `ci/typecheck`,
  `ci/test`, `ci/secrets` (gitleaks) — each job skips cleanly, and still reports success, when its area
  doesn't exist yet; **`ci/test` and the default `make test` exclude `tests/db`** (`--ignore=tests/db` or a
  deselected `db` marker) because those need a running database and run in `ci/migrations` instead;
  `make test-db` runs them locally against `supabase start`); `.github/workflows/source-branch.yml`
  (`ci/source-branch`: PRs into `main` must come from `dev`, `release/*` or `hotfix/*`);
  `.github/dependabot.yml`; `scripts/setup-branch-protection.sh` (rulesets per AGENTS_PLAN.md §15.5,
  `gh api`, idempotent, `--dry-run` flag; requires `agent-review/security` unconditionally — see below);
  `scripts/setup-labels.sh` (idempotent: `M0`–`M6`, `area:<scope>` for every scope in CLAUDE.md,
  `agent:<name>` for every agent, `security`) — **run it once** after the PR is approved so later PRs can be
  labeled; `pre-commit autoupdate`.
- **Security-gate workflow** (`.github/workflows/security-gate.yml`) — makes "`agent-review/security` required
  when it applies" enforceable by a ruleset that can only require checks unconditionally:
  - **Required when** the PR has the `security` label **OR** its diff touches a trust-boundary path:
    `supabase/functions/**`, `supabase/migrations/**`, `supabase/config.toml`, `backend/app/api/**`,
    `backend/app/serve.py`, `.github/**`, `scripts/**`, `fixtures/**`, `.env.example`, `.claude/**`.
    On a path match it also adds the `security` label, but the decision never relies on the label alone —
    removing the label cannot make a path-matched PR "not required".
  - **Never overwrites a verdict.** Before posting, read the current statuses on the head SHA. If
    `agent-review/security` already has `failure`/`error`, or a `success` not posted by this workflow, post
    nothing. The workflow only ever posts `pending` (required, no verdict yet) or `success` with description
    "not required" (not required and no verdict yet).
  - Reads labels and changed files from the API at run time (not from the event payload); per-PR
    `concurrency` group with `cancel-in-progress`.
  - Triggers: `pull_request` only — `opened`, `reopened`, `synchronize`, `ready_for_review`, `labeled`,
    `unlabeled`. Permissions: `statuses: write`, `pull-requests: write` (labeling), `contents: read`.
- Guardrails: workflows use `pull_request`, never `pull_request_target`; actions pinned by SHA; no secrets.
- Acceptance: workflows pass `actionlint` (or are validated by `gh workflow view` after push); the
  protection script prints what it would change with `--dry-run`; `gh label list` shows the label set;
  **security-gate test on a scratch PR touching `supabase/functions/`:** status goes `pending`; post a
  `failure` as security-reviewer; remove the `security` label → the check **stays red**. A scratch PR touching
  only `docs/` gets `success` "not required". Close the scratch PRs afterwards.
- Depends on: nothing.
- [ ] status

### M0.6 — CI migrations check + deploy workflows (staging + production)
- Owner: devops-engineer · Branch: `chore/m0-deploy-workflows` → PR into `dev` · Labels: `M0`, `area:devops`, `security`, `agent:devops-engineer`
- Goal: every PR proves its migrations apply to a fresh database; merging into `dev` deploys to
  `insta-saver-dev`; merging into `main` tags the release and deploys to `insta-saver-prod` — per
  `docs/AGENTS_PLAN.md` §15.4, §15.6–15.7. No deploys by hand, ever.
- Contracts: none (follows AGENTS_PLAN.md §15.4, §15.6–15.7).
- In scope:
  - `ci/migrations` job in `pr-checks.yml`: `supabase start` + `supabase db reset` in CI, then runs
    `pytest tests/db` against that database (this is where the RLS tests run); reports success (not skipped)
    when `supabase/migrations/` is empty, so it can be a required check from day one. Once migrations exist,
    pytest exit codes 4 (path missing) and 5 (no tests collected) **fail** the job.
  - `.github/workflows/deploy-staging.yml`: on push to `dev`, Environment `staging`: `supabase db push`, deploy
    Edge Functions if `supabase/functions/` has any. **Always deploys whatever is in the tree** — never decides
    "nothing to deploy" from changed paths (a commit that didn't touch migrations must still bring staging up
    to date). If **all** Environment secrets are absent (pre-H6), the job exits **successfully with a
    warning**, so `dev` doesn't go red before H6. If **some but not all** are set, it **fails** (a typo'd
    secret name must never look like a green deploy). The job summary states explicitly whether `db push`
    ran or was skipped.
  - `.github/workflows/deploy-production.yml`: on push to `main`, Environment `production`. **Order: validate
    version → deploy → tag + release notes.** Version source: look up the PR for the pushed commit via
    `gh api repos/{owner}/{repo}/commits/<sha>/pulls` (don't parse the commit message); a `release: vX.Y.Z`
    title gives the version, a `hotfix/*` head ref bumps the patch of the latest tag. If neither yields a
    valid SemVer newer than the latest tag, **fail before deploying**. If both apply, the `release:` title
    wins. The job needs `pull-requests: read` for the lookup. Unlike staging, missing secrets **fail**.
  - A placeholder smoke-test step that no-ops until M1/M2 provides the receiver.
- Guardrails: secrets only from GitHub Environments (`SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`,
  `SUPABASE_DB_PASSWORD` — confirm names in the PR and list them for the human); `permissions:` minimal per
  job (`contents: write` only for the tagging job); actions pinned by SHA; `concurrency` group so two deploys
  never overlap; no `pull_request_target`; never echo secrets.
- Out of scope: the end-to-end smoke test itself (test-engineer, M2), Edge Function code.
- Acceptance: workflows validate (`actionlint` or `gh workflow view` after push); `ci/migrations` is green
  on the PR itself; the PR description lists the exact Environment secrets the human must add.
- Depends on: **M0.2 merged** (`pr-checks.yml` exists), **M0.3 merged** (`supabase/config.toml`; same owner,
  runs after M0.3).
- [ ] status

### M0.5 — Initial schema migration
- Owner: data-engineer · Branch: `feat/m0-initial-schema` → PR into `dev` · Labels: `M0`, `area:db`, `security`, `agent:data-engineer`
- Goal: the first migration creates the tables, indexes and RLS defined in the schema contract, so staging
  and production start from the same database shape.
- Contracts: `docs/contracts/schema.md`, `docs/contracts/storage.md` (from M0.1). Implement them exactly — any
  gap or ambiguity goes back to `architect`, not into the migration.
- In scope: `supabase/migrations/<timestamp>_initial_schema.sql` — tables, constraints, indexes; **RLS enabled
  on every table with no policies** (access only via the service role, per PLAN.md §6) unless `schema.md`
  explicitly defines a policy; Storage bucket + policies only if `storage.md` defines them;
  `supabase/seed.sql` with synthetic rows only; `tests/db/` checks that the migration applies cleanly and
  that, for every table in `schema.md` **without an explicit policy**, the `anon` and `authenticated` roles
  can neither read nor write (tables with a policy get a test for exactly that policy). The db tests **fail,
  not skip**, when no database is reachable — they run in `ci/migrations` (M0.6).
- Out of scope: pg_cron jobs (M2), `backend/app/db/repo.py` / `storage.py` (M3), search indexes beyond
  what `schema.md` lists (M5).
- Acceptance: `supabase db reset` applies migration + seed with no errors; db tests pass; `ci/migrations`
  green on the PR; no real personal data in `seed.sql`; after merge, the `deploy-staging` run is green **and
  its summary shows `db push` ran** (not the no-secrets skip).
- Depends on: **M0.1 merged** (contracts), **M0.6 merged** (so CI checks and deploys it), **HUMAN H6 done**
  (so the merge actually lands on staging). Can be built and reviewed in parallel; **merge waits** on these.
- [ ] status
