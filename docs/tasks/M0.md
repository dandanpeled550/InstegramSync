# M0 — Setup

**Goal:** the repo, tooling, contracts and accounts are ready, so M1 can start building the receiver.
**Done when:**
1. M0.5 (initial schema) merges into `dev` with every required check green (incl. `ci/migrations`), and the
   resulting `deploy-staging` run is green — the schema is live on `insta-saver-dev`.
2. Release `v0.1.0` is merged into `main` by the human, and the resulting `deploy-production` run is green
   and created the `v0.1.0` tag.

This refines `docs/PLAN.md` §9 ("first PR merged into `dev` deploys to staging"): PR #1 merged before CI
existed, so the criterion is tied to the first PR that has something to deploy.

### M0.6 — CI migrations check + deploy workflows (staging + production)
- Owner: devops-engineer · Branch: `chore/m0-deploy-workflows` → PR into `dev` · Labels: `M0`, `area:devops`, `security`, `agent:devops-engineer`
- Goal: every PR proves its migrations apply to a fresh database; merging into `dev` deploys to
  `insta-saver-dev`; merging into `main` tags the release and deploys to `insta-saver-prod` — per
  `docs/AGENTS_PLAN.md` §15.4, §15.6–15.7. No deploys by hand, ever.
- Contracts: none (follows AGENTS_PLAN.md §15.4, §15.6–15.7).
- In scope:
  - `ci/migrations` job in `pr-checks.yml`: `supabase start` + `supabase db reset` in CI; reports success
    (not skipped) when `supabase/migrations/` is empty, so it can be a required check from day one.
  - `.github/workflows/deploy-staging.yml`: on push to `dev`, Environment `staging`: `supabase db push`, deploy
    Edge Functions if `supabase/functions/` has any. **Always deploys whatever is in the tree** — never decides
    "nothing to deploy" from changed paths (a commit that didn't touch migrations must still bring staging up
    to date). If the Environment secrets aren't set yet, the job exits **successfully with a warning**, so
    `dev` doesn't go red before H6.
  - `.github/workflows/deploy-production.yml`: on push to `main`, Environment `production`: same deploy, then
    tag + release notes. **Version source:** the merged PR title `release: vX.Y.Z` (squash or merge commit
    message); a hotfix push (`hotfix/*` merge) bumps the patch of the latest tag. Fail loudly if neither yields
    a valid SemVer that's newer than the latest tag. Unlike staging, missing secrets **fail** here.
  - A placeholder smoke-test step that no-ops until M1/M2 provides the receiver.
- Guardrails: secrets only from GitHub Environments (`SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`,
  `SUPABASE_DB_PASSWORD` — confirm names in the PR and list them for the human); `permissions:` minimal per
  job (`contents: write` only for the tagging job); actions pinned by SHA; `concurrency` group so two deploys
  never overlap; no `pull_request_target`; never echo secrets.
- Out of scope: the end-to-end smoke test itself (test-engineer, M2), Edge Function code.
- Acceptance: workflows validate (`actionlint` or `gh workflow view` after push); `ci/migrations` is green
  on the PR itself; the PR description lists the exact Environment secrets the human must add.
- Depends on: **M0.2 merged** (`pr-checks.yml` exists), **M0.3 merged** (`supabase/config.toml`; same owner,
  runs after M0.3).
- [ ] status

### M0.5 — Initial schema migration
- Owner: data-engineer · Branch: `feat/m0-initial-schema` → PR into `dev` · Labels: `M0`, `area:db`, `security`, `agent:data-engineer`
- Goal: the first migration creates the tables, indexes and RLS defined in the schema contract, so staging
  and production start from the same database shape.
- Contracts: `docs/contracts/schema.md`, `docs/contracts/storage.md` (from M0.1). Implement them exactly — any
  gap or ambiguity goes back to `architect`, not into the migration.
- In scope: `supabase/migrations/<timestamp>_initial_schema.sql` — tables, constraints, indexes; **RLS enabled
  on every table with no policies** (access only via the service role, per PLAN.md §6) unless `schema.md`
  explicitly defines a policy; Storage bucket + policies only if `storage.md` defines them;
  `supabase/seed.sql` with synthetic rows only; `tests/db/` checks that the migration applies cleanly and
  that, **for every table in `schema.md`**, the `anon` and `authenticated` roles can neither read nor write.
- Out of scope: pg_cron jobs (M2), `backend/app/db/repo.py` / `storage.py` (M3), search indexes beyond
  what `schema.md` lists (M5).
- Acceptance: `supabase db reset` applies migration + seed with no errors; db tests pass; `ci/migrations`
  green on the PR; no real personal data in `seed.sql`; after merge, the `deploy-staging` run is green.
- Depends on: **M0.1 merged** (contracts), **M0.6 merged** (so CI checks and deploys it), **HUMAN H6 done**
  (so the merge actually lands on staging). Can be built and reviewed in parallel; **merge waits** on these.
- [ ] status
