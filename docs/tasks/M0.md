- Owner: architect · Branch: `docs/m0-contracts-v0` → PR into `dev` · Labels: `M0`, `area:contracts`
- Goal: the contracts and decisions every later milestone builds against.
- In scope: `docs/contracts/{schema,interfaces,api,storage}.md`; ADRs 0001–0003 (see `docs/decisions/README.md`).
- Source: `docs/PLAN.md` §2–§7, `docs/AGENTS_PLAN.md` §15.
- Acceptance: schema matches PLAN.md §6; interfaces are typed Python protocols/dataclasses with docstrings;
  `api.md` lists all endpoints from PLAN.md §7 with request/response JSON; each ADR uses the template.
- Depends on: nothing. **Must merge before any M1 builder starts.**
- [ ] status

### M0.2 — CI, tooling, branch protection script
- Owner: devops-engineer · Branch: `chore/m0-ci-tooling` → PR into `dev` · Labels: `M0`, `area:devops`, `security`
- In scope: `Makefile` (targets: `dev`, `test`, `lint`, `fmt`, `process`, `process-prod` stub with the
  main/clean/tag check, `replay` stub); `.github/workflows/pr-checks.yml` (lint, typecheck, test, gitleaks —
  each job skips cleanly when its area doesn't exist yet); `.github/workflows/source-branch.yml`
  (`ci/source-branch`: PRs into `main` must come from `dev`, `release/*` or `hotfix/*`);
  `.github/dependabot.yml`; `scripts/setup-branch-protection.sh` (rulesets per AGENTS_PLAN.md §15.5,
  `gh api`, idempotent, dry-run flag); `pre-commit autoupdate`.
- Guardrails: workflows use `pull_request`, never `pull_request_target`; actions pinned by SHA; no secrets.
- Acceptance: workflows pass `actionlint` (or are validated by `gh workflow view` after push); the
  protection script prints what it would change with `--dry-run`.
- Depends on: nothing.
- [ ] status

### M0.5 — Initial schema migration
- Owner: data-engineer · Branch: `feat/m0-initial-schema` → PR into `dev` · Labels: `M0`, `area:db`, `security`
- Goal: the first migration creates the tables, indexes and RLS defined in the schema contract, so staging
  and production start from the same database shape.
- Contracts: `docs/contracts/schema.md`, `docs/contracts/storage.md` (from M0.1). Implement them exactly — any
  gap or ambiguity goes back to `architect`, not into the migration.
- In scope: `supabase/migrations/<timestamp>_initial_schema.sql` (tables, constraints, indexes, RLS enabled
  with deny-by-default policies, Storage bucket + policies if `storage.md` defines them); `supabase/seed.sql`
  with synthetic rows only; `tests/db/` checks that the migration applies cleanly on `supabase start`
  and that RLS blocks the `anon` role.
- Out of scope: pg_cron jobs (M2), `backend/app/db/repo.py` / `storage.py` (M3), search indexes beyond
  what `schema.md` lists (M5).
- Acceptance: `supabase db reset` applies the migration and seed with no errors locally; the db tests pass;
  no real personal data in `seed.sql`.
- Depends on: **M0.1 merged** (contracts), **M0.3 merged** (`supabase/config.toml`).
- [ ] status

### M0.6 — CI deploy workflows (staging + production)
- Owner: devops-engineer · Branch: `chore/m0-deploy-workflows` → PR into `dev` · Labels: `M0`, `area:devops`, `security`
- Goal: merging into `dev` deploys to `insta-saver-dev`; merging into `main` tags the release and deploys to
  `insta-saver-prod` — per `docs/AGENTS_PLAN.md` §15.6–15.7. No deploys by hand, ever.
- In scope: `.github/workflows/deploy-staging.yml` (on push to `dev`: `supabase db push` + deploy Edge
  Functions if `supabase/functions/` has any, GitHub Environment `staging`); `.github/workflows/deploy-production.yml`
  (on push to `main`: same against Environment `production`, then create tag `vX.Y.Z` and release notes);
  a skip-cleanly path when there's nothing to deploy; a placeholder smoke-test step that no-ops until M1/M2
  provides the receiver.
- Guardrails: secrets only from GitHub Environments (`SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`,
  `SUPABASE_DB_PASSWORD` — confirm names in the PR and list them for the human); `permissions:` minimal per
  job (`contents: write` only for the tagging job); actions pinned by SHA; `concurrency` group so two deploys
  never overlap; no `pull_request_target`; never echo secrets.
- Out of scope: the end-to-end smoke test itself (test-engineer, M2), Edge Function code.
- Acceptance: workflows validate (`actionlint` or `gh workflow view` after push); the PR description lists
  the exact Environment secrets the human must add; first merge into `dev` after H6 shows a green staging
  deploy run.
- Depends on: **M0.2 merged** (shared workflow conventions), **HUMAN H6** (projects + Environment secrets)
  before the first real run; the PR itself can be built and reviewed before H6.
- [ ] status
